### [2026-10-12] E2: a supplied answer is a miss (option B)
* **Options put to the user** (with the lab's simulated children re-judged
  under each): B count it as a miss; C leave supplied answers out of the rate;
  D keep the rate, block mastery above 10% supplied. **User chose B** ("the only
  solution"). C still let struggling children reach mastery (7 sessions in the
  lab's class); D left the gross-shape → feature step flattered.
* **Trade-off accepted:** strong children master slightly less often (lab:
  104 → 86 mastery sessions), because one supplied answer now costs what one
  wrong tap does. The 10% / 30% thresholds are unchanged.

### [2026-10-12] Existing records: judged again on every read (option c)
* **Options:** (a) leave old labels, which correct as letters are replayed;
  (b) the same, plus pages the child played on stay open; (c) re-judge every
  old session now. **User chose c**, then also asked that played-on pages stay
  open.
* **How:** on read, not by rewriting — `letterStatuses()` derives each status
  from the saved answers. Rewriting saved history would have needed the rules'
  second confirmation (§11); judging on read corrects every child at once and
  keeps doing so if the rule changes again. Cost: the roadmap and adult home
  read all of a child's sessions (≤1,000) — revisit for class views (W4b/W5c).

### [2026-10-12] E3: a mix-up counts for both letters — the check question
* **User's brief:** "if a child confuses ba and ka, shouldn't data for both be
  affected?" A "needs review" flag (badge, review sessions) was too complex;
  taking mastery away on a mix-up too extreme. **Chosen middle ground:** two
  unaided mistaken picks of a mastered letter earn it one check question (last
  Listen & tap question of the next session, among the letters it was mistaken
  for). The check's first answer decides: right keeps mastery, wrong or
  supplied returns it to still learning until the child next plays it.
* **Tunable:** `CHECK_AFTER_PICKS = 2`, one check per session. No new UI.

### [2026-10-10] Accounts: adults own children; classes and share codes; PIN lock (W5)
* **Context:** one Google account was one child (`user_profiles.id` = auth
  uid, every RLS rule `auth.uid() = user_id`). The Parent and Teacher buttons
  ran identical code, and the adult area was guarded by a sum a child can do.
* **Decisions (user-chosen from presented options):**
  1. **Adults sign in; children are profiles adults own.** No child logins.
     Rejected: children keeping their own Google logins — impractical for
     5–8 year olds and shared classroom devices.
  2. **Teachers get named classes, and both roles get share codes** — the most
     complete of the three options offered. A class code lets a parent add
     their child to a teacher's class (making the teacher a guardian); a child
     share code lets another adult claim guardianship of an existing child.
  3. **A 4-digit adult PIN** replaces the addition gate. Reset by signing in
     with Google again.
* **Schema strategy (proposed with the plan):** keep `user_id` on
  `learning_sessions` / `letter_progress` as the *subject* and re-point its
  foreign key at a new `children` table. Every existing account becomes a
  parent whose one child has the account's own id, so no row is rewritten and
  the deployed client keeps working through the transition.

### [2026-10-09] GitHub auth via an SSH key, not `gh` and not a PAT
* **Context:** no credential on the machine could push. 15 commits holding the
  entire P1–P6 refactor and structure cleanup existed only on this laptop, which
  was the single largest standing risk in the project.
* **Options weighed:** (1) an ed25519 SSH key; (2) `brew install gh` plus
  `gh auth login`; (3) a fine-grained PAT stored in the keychain.
* **Decision:** option 1, generated with **no passphrase** so pushes stay
  non-interactive, and `origin` switched to SSH. Nothing is installed, nothing
  expires, and the private key never leaves the machine.
* **Trade-offs accepted:** no `gh`, so PR and issue work from the CLI would need
  that install later. A passphrase-less key means the file itself is the secret,
  protected by `0600` and FileVault — standard for a personal laptop, and the
  alternative was typing a passphrase or caching it in the keychain anyway.
  A PAT was rejected because it expires within a year and because pasting a token
  through an agent shell risks leaving it in history or a transcript.
* **Rejected, for the record:** retrying HTTPS. The keychain held no
  `host=github.com` entry at all by this session, so the documented
  `Invalid username or token` symptom would not even have reproduced — an HTTPS
  push blocks on a username prompt instead.

### [2026-07-05] Dotless tracing canvas and scored drawing
* **Context:** Visual dots and magnetic lassoing distract children and inflate

  "Clear Canvas" and "Check Drawing".
