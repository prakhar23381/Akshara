## 4. Reference Decisions  *(append-only — never prune)*

### [2026-10-10] Accounts: adults own children; classes and share codes; PIN lock (W5)
* **Context:** one Google account was one child (`user_profiles.id` = auth
  uid, every RLS rule `auth.uid() = user_id`). The Parent and Teacher buttons
  ran identical code, and the adult area was guarded by a sum a child can do.
* **Decisions (user-chosen from presented options):**
  1. **Adults sign in; children are profiles adults own.** No child logins.
     Rejected: children keeping their own Google logins — impractical for
     5–8 year olds and shared classroom devices.
  2. **Teachers get named classes, and both roles get share codes** — the most
     complete of the three options offered. A class code lets a parent add
     their child to a teacher's class (making the teacher a guardian); a child
     share code lets another adult claim guardianship of an existing child.
  3. **A 4-digit adult PIN** replaces the addition gate. Reset by signing in
     with Google again.
* **Schema strategy (proposed with the plan):** keep `user_id` on
  `learning_sessions` / `letter_progress` as the *subject* and re-point its
  foreign key at a new `children` table. Every existing account becomes a
  parent whose one child has the account's own id, so no row is rewritten and
  the deployed client keeps working through the transition.

### [2026-10-10] Report becomes a dashboard grid (W4)
* **Context:** the adult report followed the child no-scroll rule, split thin
  content across three tabs and stretched sections to fill the screen, while
  per-letter error rate, trend, error series, confusions, strengths, focus
  areas and per-letter notes were computed and rendered nowhere.
* **Decision (user-chosen):** a dashboard grid of cards — 2–3 columns on
  tablet and desktop, one column on a phone — on a page that scrolls. Adult
  screens are exempt from the child no-scroll rule.
* **RAG bands (proposed):** the engine's own 10% / 30% error thresholds, so a
  colour always marks a point at which the app changes the child's level.

### [2026-10-10] Error magnitude DOES get red/amber/green — reversing the 2026-10-06 restraint
* **Context:** device feedback called the learning report colourless. The
  2026-10-06 entry below had deliberately kept error magnitude single-hue,
  encoded by bar length, on the grounds that this tool has no validated cut-off
  scores and colouring 30% "red" asserts a clinical threshold it has not earned.
* **The conflict was put to the user explicitly, with that reasoning, and the
  user chose to overturn it.** RAG colour goes on scores.
* **Decision:** supersede the single-hue rule. The 2026-10-06 bullet stays below
  as the record of what was reversed and why — it is append-only — but it is **no
  longer the governing rule** for the report.
* **Trade-off accepted, and it is the user's to accept:** the report now
  implies thresholds the project has not validated, which is exactly the thing
  that made the old design defensible to a specialist. If a clinician ever asks
  what the amber band means, there is no answer yet. Worth revisiting once there
  are real cut-offs.

### [2026-10-10] Matras become first-class, not just correctly split
* **Context:** report 9, that matras appear on the letter rather than
  separately. Investigation found no matra concept in the codebase at all: words
  are split by code point, so a matra is treated as if it were a letter.
* **Decision:** do both halves. Fix the grapheme handling (`Intl.Segmenter`),
  *and* add a teaching model that presents bare consonant, matra mark and
  combined form as three distinct things, the way Hindi teaching does.
* **Consequence to plan for:** the teaching half is new content across 33
  letters and probably a new activity, so it is scoped separately from the
  correctness fix. The correctness fix is urgent on its own: ङ and ञ currently
  record attempts under the wrong letter, which pollutes the adaptive engine.

### [2026-10-10] Child-facing work goes on a branch, never straight to main
* **Context:** a push to `main` is a production release (see §3). W1 is
  child-facing UI that cannot be verified without a browser.
* **Decision:** W1 and the phases after it land on feature branches. `main` only
  receives them once the device checks pass. A branch push still gets a Vercel
  *preview* deployment, which is the artifact to test on a phone.

### [2026-10-09] GitHub auth via an SSH key, not `gh` and not a PAT
* **Context:** no credential on the machine could push. 15 commits holding the
  entire P1–P6 refactor and structure cleanup existed only on this laptop, which
  was the single largest standing risk in the project.
* **Options weighed:** (1) an ed25519 SSH key; (2) `brew install gh` plus
  `gh auth login`; (3) a fine-grained PAT stored in the keychain.
* **Decision:** option 1, generated with **no passphrase** so pushes stay
  non-interactive, and `origin` switched to SSH. Nothing is installed, nothing
  expires, and the private key never leaves the machine.
* **Trade-offs accepted:** no `gh`, so PR and issue work from the CLI would need
  that install later. A passphrase-less key means the file itself is the secret,
  protected by `0600` and FileVault — standard for a personal laptop, and the
  alternative was typing a passphrase or caching it in the keychain anyway.
  A PAT was rejected because it expires within a year and because pasting a token
  through an agent shell risks leaving it in history or a transcript.
* **Rejected, for the record:** retrying HTTPS. The keychain held no
  `host=github.com` entry at all by this session, so the documented
  `Invalid username or token` symptom would not even have reproduced — an HTTPS
  push blocks on a username prompt instead.

### [2026-07-05] Automated sequential game flow
* **Context:** The student should not have to choose between activities.
* **Decision:** One linear flow per letter. *Superseded in form by P3 — the
  navigation is now a step machine at `/play` derived from `levelConfig`, not a
  chain of `navigate()` calls — but the pedagogical intent still holds.*

### [2026-07-05] Student-specific similarity card matching
* **Context:** The card game should match visually similar letters, customised
  to what each student actually confuses.
* **Decision:** Match identical glyphs (`भ` vs `भ`), pulling distractors from the
  student's own `confused_with` history and falling back to a static visual
  similarity index.

### [2026-07-05] Dotless tracing canvas and scored drawing
* **Context:** Visual dots and magnetic lassoing distract children and inflate
  accuracy.
* **Decision:** No guide dots. Sample the path at spacing 10, score by grid-based
  Jaccard similarity so a wrong character or a scribble cannot pass, and offer
  "Clear Canvas" and "Check Drawing".
